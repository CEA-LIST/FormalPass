# SMT-based program analysis for renaming SMT variables and merging SMT models 

## Why do we need to merge SMT models into one?

When analyzing programs with function calls, each function generates its own SMT formula with local variable names (e.g., `bb0`, `t_0_1`, `m_2_3`). Naively combining these creates variable name conflicts: multiple functions have variables with the same names but different meanings.

Creating one unified SMT formula for the entire input application facilitates:
1. Whole program analysis:
    - captures inter-procedural behavior.
    - analyzes how function calls interact and accumulate costs.
    - accounts for call chains: main->fft->stockham costs cascade upward.
2. Constraint propagation:
    - SMT solver propagates constraints through the entire program.
    - discovers hidden dependencies between conditions and costs.
3. Precise path exploration:
    - SMT solver explores all feasible paths of the entire input application simultaneously.
    - finds paths that maximize/minimize properties.

## Our solution:

Our approach uses context-sensitive renaming with bottom-up merging.
- no variable conflicts: each call site gets unique variable names.
- context-sensitive: different calls to the same function are distinguished.
e.g. `fft_bb7_stockham_0`: `fft` is the caller function, `bb7` is the basic block where the function call took place, `stockham` is the callee function and finally `0` is the occurence number of the function call (the same function could be called more than once inside the same basic block. Each call needs to be distinguished, hence the occurence number of the call.). 
- compositional: each merge creates a valid, complete formula.
- tractable: bottom-up avoids exponential explosion of paths.

## How does it work?
1. Call graph depth analysis:

    main (depth 2)
    
    |__ fft (depth 1)
        
        |__ stockham (depth 0)

    - leaf functions (no calls): depth 0
    - functions calling only leaves: depth 1
    - process from leaves -> root

2. Iterative merge and rename:

    - Step 1: Start with leaf (stockham)

    ```
    smt(declare-fun bb0 () Bool)
    (declare-fun m_4_5 () Int)
    (assert (= mem_cost (+ m_0_1 ... m_4_5)))

    ```

    - Step 2: Merge stockham into fft

        - Rename ALL stockham variables with call-site prefix: `fft_bb7_stockham_0_`

        `bb0 -> fft_bb7_stockham_0_bb0`
    
        `m_4_5 -> fft_bb7_stockham_0_m_4_5`
    
        `mem_cost -> fft_bb7_stockham_0_mem_cost`


        - Add linking constraint:

        `smt  (assert (= fft_bb7_stockham_0 fft_bb7_stockham_0_bb0))`

        - Absorb memory cost:

        ```

        smt  (declare-fun m_7_exit_with_calls () Int)
        (assert (= m_7_exit_with_calls 
                    (ite t_7_exit 
                        (+ m_7_exit fft_bb7_stockham_0_mem_cost) 
                        0)))
                        
        ```

        - Update fft's mem_cost:

        `smt  (assert (= mem_cost (+ ... m_7_exit_with_calls ...)))`

        => Result: *merged_fft.smt*: a complete, self-contained formula.

    - Step 3: merge *merged_fft.smt* into main

        - rename all *fft* variables (including already-prefixed ones): `main_bb0_fft_0_`

        `fft_bb7_stockham_0_bb0 -> main_bb0_fft_0_fft_bb7_stockham_0_bb0`

        `m_7_exit_with_calls -> main_bb0_fft_0_m_7_exit_with_calls`


        - add linking and absorption (same process)

        => final Result: *main_merged.smt*: one formula for the entire program.
        


### How to invoke the postprocessing function?

This script uses call graph files (.txt files) (e.g. *fft.txt*, presented hereafter) containing a list of function calls as well as smt files, all of them are generated by the *RISCVmirToSMTfctCallLoopBound* pass. 

```
***    fft.txt ***
# smt_lib2_fft.smt
fft_bb3___assert_fail_0
fft_bb4_malloc_0
fft_bb6___assert_fail_0
fft_bb7_stockham_0
fft_bb7_free_1

```

Thus, the script should be called after compiling the input application with the *RISCVmirToSMTfctCallLoopBound* pass: 

`path/to/build/bin/clang   --target=riscv64 -march=rv64gc -emit-llvm  -I/usr/include MyTests/fft.c -c -o MyTests/fft.bc`

`path/to/build/bin/llc  -stats -smt-generation-fct-call-loop-bound --march=riscv64 MyTests/fft.bc  -o MyTests/fft.s`

The entry point (command line argument) is simply the name of the main function: e.g. *main*.

`chmod +x merge_smt.sh` 

`./merge_smt.sh main` 

This will create:

- *work_smt/* directory with renamed SMT files.
- *main_merged.smt* the final unified SMT file.

## Files the script ignores:

System Functions (No `.smt` file exists)
From our *fft* example:

- `__assert_fail` (from fft.txt)
- `malloc` (from fft.txt)
- `free` (from fft.txt)
- `cos` (from stockham.txt)
- `sin` (from stockham.txt)
- `llvm.fmuladd.f64` (from stockham.txt)
- `llvm.memcpy.p0.p0.i64` (from stockham.txt)

These are automatically skipped** because no corresponding `smt_lib2_<function>.smt` file exists.
